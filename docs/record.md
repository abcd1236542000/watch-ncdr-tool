## 1. 專案一句話定義 〔參考·現況〕

把官網的「雨量雲圖 × 時間軸」，轉成使用者所選**鄉鎮**的「**時間 × 雨量等級**」表格，一眼看出何時下雨、雨勢多大。

### 2.1 DOM 關鍵元素

| 元素 | 說明 |
| --- | --- |
| `#TAIWAN_TOWN_id_1_p` (`.domain_parent_cls`) | 最外層容器 |

### 2.2 鄉鎮 SVG 圖層（工具的地理資料唯一來源）

- `svg[0]` 內含 **367 條鄉鎮 path**，涵蓋 **22 縣市**
- 每條 path 掛有 D3 綁定資料：
  - `path.__data__.properties.{COUNTYNAME, TOWNNAME}`
  - `path.__data__.geometry`（GeoJSON，**經緯度**座標，Polygon / MultiPolygon）
- 各縣市鄉鎮數實測：高雄38、台南37、屏東33、新北29、台中29、彰化26、雲林20、苗栗18、嘉義縣18、台東16、桃園13、南投13、新竹縣13、花蓮13、宜蘭12、台北12、基隆7、澎湖6、金門5、連江4、新竹市3、嘉義市2
- **重要**：工具**完全不需外部圖資**，縣市/鄉鎮清單、紅框、命中判定全由此 SVG 現場取得

### 2.3 影像清單 API

- 端點：`https://watch.ncdr.nat.gov.tw/appv2/module/nowcast/api/cv_ncdrnowcast_appinfo_v2`
  - ⚠️ 曾誤用 `/api/v2/cv_ncdrnowcast_appinfo_v2` → 404
- 格式：CSV，欄位 `[id, timestamp, file, status, lgtfile]`
- `id`：`-3 ~ -1` 為觀測、`0 ~ 12` 為預報 → 共 16 格，每格 10 分鐘

### 2.4 影像檔規格

- 尺寸：**3300 × 2550 px**（兩種模式的原生尺寸相同）
- 地理範圍：經度 `117.1595 ~ 123.9804`、緯度 `21.2646 ~ 26.5353`
- 像素換算：
  ```
  x = (lon - 117.1595) / (123.9804 - 117.1595) * 3300
  y = (26.5353 - lat) / (26.5353 - 21.2646) * 2550
  ```
- 檔名時間為 **UTC**，台灣時間 = UTC + 8
- 兩種影像**檔名不同**（見 §2.5）

### 2.5 【關鍵】兩種顯示模式 — 左下角按鈕切換

左下角按鈕在「**展開 / 雷達回波**」與「**雨量**」兩狀態間切換，**兩者是不同的 `<img>` 元素、不同的檔案、不同的色盤**：

> v1.0 的色盤抄自 dBZ 回波圖（該圖白色才是最強回波），連帶使
> 「白色候選豪雨」補丁（舊 §6.2）建立在錯誤前提上，v1.1 起已移除。

> 🔴 **翻案二**（v1.4）：v1.1–v1.3 假設「每帶一階、未標籤者內插」，推估出
> 0.15 / 0.6 / 1.25 / 2.2 … 等值，**全部是錯的**。正確是**兩帶一階**。

（透明 96.2%，其餘全部落在 17 色帶內）→ 色盤完整無缺漏。

### 2.7 同源限制（為何非得是 Bookmarklet）

NCDR 的雷達圖 PNG **沒有 `Access-Control-Allow-Origin` 標頭**，跨網域無法用 canvas 讀像素（CORS 污染）。
故工具必須在**同源**（官網頁面）情境執行。已評估並否決：獨立網頁（CORS 不可行）、代理伺服器（過重）、改用 CWA API（偏離需求）。

### 2.9 【v1.1 關鍵】座標對應的權威錨點：`.domain_cls`

工具需要「螢幕座標 ↔ 經緯度」的換算基準。**實測踩過兩個坑後**才定案：

| 候選錨點 | 結果 |
| --- | --- |
| `svg[0]`（鄉鎮圖層）| ❌ `width`/`height` 寫死 1600×1236，模式切換不重算 |
| `#TAIWAN_DBZ_PIC` (`<img>`) | ❌ 兩個致命問題，見下 |
| **`.domain_cls` (`#TAIWAN_TOWN_id_1_do`)** | ✅ **採用** |

**為何不能用底圖 `<img>`**（v1.1 開發時實際踩到）：

1. **時間軸播放時 `<img>` 會被抽換**，短暫不存在 → `getRaster()` 回傳 null
2. **`#TAIWAN_DBZ_PIC` 的祖先 `#TAIWAN_DBZ_id` 帶 3D 透視變換**：
   ```
   transform: matrix3d(0.7, 0, 0, 0, 0, 0.33, 0, -0.00225, 0, 0, 1, 0, 0, 0, 0, 1.1)
   ```
   其 `getBoundingClientRect()` 回傳的是**投影後梯形的外接框**（實測長寬比 4.66，
   而非應有的 1.294）→ 非線性映射，數學上不可用

**`.domain_cls` 的驗證**：長寬比實測 **1.2941**，與影像 3300/2550 = **1.2941 完全相同**，
證明它正是「完整地理範圍」的視窗容器。且會隨模式切換正確變動：

| 模式 | `.domain_cls` rect |
| --- | --- |
| 雨量 | [307, 0, 884, 683] |
| 雷達回波 | [0, -293, 1600, 1236] |

換算式：
```js
fx = (screenX - rect.left) / rect.width
fy = (screenY - rect.top)  / rect.height
lon = 117.1595 + fx * (123.9804 - 117.1595)
lat = 26.5353  - fy * (26.5353  - 21.2646)
```

### 2.10 官網 CSP 白名單（2026-07-28 實測，決定「能不能載外部資料」）

`curl -I https://watch.ncdr.nat.gov.tw/appv2/` 取得的 `content-security-policy`，摘出與本工具有關的三條：

| 指令 | 相關白名單 | 對工具的意義 |
| --- | --- | --- |
| `script-src-elem` | `'self'`、`blob:`、`cdn.jsdelivr.net`、`unpkg.com`、`code.jquery.com`、`api.mapbox.com`… | **可以**用 `<script src>` 從 jsDelivr／unpkg 載外部程式碼或資料（實測 `cdn.jsdelivr.net/gh/…` 載入成功）|
| `connect-src` | `'self'`、`data:`、少數第三方（google-analytics、mapbox、arcgisonline…）| **不可以** `fetch()` 外部網域。實測 `raw.githubusercontent.com`、`*.github.io` 皆 `Failed to fetch` |
| `img-src` | `'self'`、`data:`、少數政府／YouTube 網域 | 外部圖片也載不進來；雷達 PNG 是同源，不受影響 |

**推論**：若日後要載村里等外部圖資（§12.9），只能包成 `<script>` 可執行的 JS 檔（例如
`window.__RH_VILL_xxx = {...}`）並託管在 jsDelivr／unpkg，**不能用 fetch 拉 JSON**。
同一結論也適用於 §8 的「loader 架構」構想。

**2026-07-28 於官網頁面實測三件事**（直接決定本機測試怎麼做，見 §13.10）：

| 嘗試 | 結果 |
| --- | --- |
| `<script src="http://localhost:8765/…">` | **BLOCKED**（`script-src-elem` 不含 localhost）|
| `fetch('http://localhost:8765/…')` | **BLOCKED**（`connect-src` 不含 localhost）|
| `<script src="blob:…">` | **LOADED**（`script-src-elem` 白名單首項就是 `blob:`）|

→ 本機檔案無法直接餵給官網頁面；但 CSP 只檢查**請求 URL**，
所以 DevTools Local Overrides（URL 仍是 jsDelivr、回應換成本機檔案）可以通。

> ⚠️ 這是官網的設定，隨時可能變動；依賴它就等於把工具的可用性押在別人的 header 上。

## 4. 目前狀態與待修問題 〔參考·現況〕

> ## ✅ v1.1 已全數修復（2026-07-18）
> §4.1 / §4.3 兩個 Bug 已修正並實機驗證通過。以下保留原始診斷紀錄供追溯。

### 4.1 ✅ 【已修復 v1.1】點地圖選點回報「該點不在任何鄉鎮範圍內，請重試」

**症狀**：使用「點地圖選點」時，點在台灣本島上卻回報不在任何鄉鎮範圍內。

**根因（實測確認）**：SVG 圖層與底圖雨圖的**縮放比例不一致**。

實測數據（雨量模式下）：

| 元素 | 螢幕實際尺寸 | 位置 |
| --- | --- | --- |
| 底圖 `#BK_RAIN_id` | 881.9 × 683 px | x≈309, y=1 |
| 鄉鎮 `svg[0]` | **1600 × 1236 px** | x≈308, y=1 |

- 縮放比 1600 / 881.9 = **1.814**；1236 / 683 = **1.810**（一致）
- 兩者左上角同錨點，故**離左上角越遠偏移越大**
- 台灣本島位於畫面中右方 → 偏移最嚴重 → 點擊落在所有 path 之外 → `isPointInFill` 全數 miss

**與左下角按鈕的關係（使用者原始猜測，已證實）**：

| 模式 | SVG rect | 底圖 rect | `isPointInFill` |
| --- | --- | --- | --- |
| 雷達回波（收合）| [1, -275, 1600, 1236] | [1, -275, 1600, 1236] | ✅ 正常 |
| 雨量（展開）| [308, 1, 1600, 1236] | [309, 1, **881.9, 683**] | ❌ 全 miss |

- 切換時容器尺寸實測由 `958×741` 變為 `886×685`
- 但 SVG 的 `width` / `height` 屬性**固定寫死 1600×1236，從未重算**
- 官網只在初始化時算一次投影，版面變動不同步
- **右下角 GPS 鈕無關**

**驗證證據**：
- 雷達回波模式：`hit(790,300)` → 彰化縣彰化市 ✅、`hit(850,450)` → 嘉義縣阿里山鄉 ✅
- 雨量模式：`hit(790,300)` → `-1` ❌、`hit(850,450)` → `-1` ❌、`hit(1280,400)` → 新北市（落在畫面右側的「幽靈地圖」上）

### 4.2 ✅ 已驗證的修正方向

**放棄依賴 SVG 螢幕座標**，改用「底圖矩形 → 經緯度 → GeoJSON 命中」三段式：

1. 取當前作用中的底圖 `<img>` 矩形（`#BK_RAIN_id` 或 `#TAIWAN_DBZ_PIC`，取可見者）
2. 點擊螢幕座標 → 該矩形內的相對比例 → 經緯度（用 §2.4 地理範圍）
3. 經緯度 → 對 367 條 path 的 `__data__.geometry` 做射線法 point-in-polygon（含 hole 處理）

**已在實際頁面試跑驗證**：

| 點擊座標 | 換算經緯度 | 判定結果 |
| --- | --- | --- |
| (790, 300) | 120.878, 24.228 | 台中市東勢區 ✅ |
| (850, 450) | 121.342, 23.070 | 台東縣成功鎮 ✅ |
| (720, 250) | 120.337, 24.614 | 海上（正確回報無命中）✅ |

**優點**：對容器縮放、模式切換、視窗 resize **全免疫**，因為底圖 PNG 矩形永遠是權威來源。

**連帶必須同步修正**：紅框繪製目前是 clone 官網 path，在雨量模式下同樣會畫錯位置 → 需改為由經緯度反推螢幕座標繪製，或僅在座標系一致時才 clone。

### 4.3 ✅ 【已修復 v1.1】取樣的是 dBZ 影像，卻套用雨量色盤

**已由實測確認，非推測。**

API 的 `file` 欄位（`c[2]`）回傳的是 **dBZ 雷達回波**檔名：

```
-3,...,/00_Wxmap/7F13_NOWCAST/OBS/202607/20260718/obs_s202607181500.png,1,...
 0,...,/00_Wxmap/7F13_NOWCAST/202607/20260718/202607181530/nowcast_202607181530_s00.png,1,...
```

而 `bm.js` 的 `runQuery()` 直接取用該欄位組 URL 送進 `sampleImage()`，
再用 `classify()` 的**雨量色盤**（0.3 / 1.5 / 6 / 17 mm 級距）判讀 →
**色彩語意錯配**，輸出的 mm 值不具意義。

**修正**：組 URL 時將檔名 `.png` 換成 `_rain.png`：

```js
var fn = (c[2]||'').replace(/^"|"$/g,'').replace(/\.png$/i, '_rain.png');
```

並保留 fallback：若 `_rain` 版 404 則退回原檔並在 UI 標註為「回波強度推估」。

## 5. 系統架構與運作流程 〔參考·現況〕

```
使用者操作（下拉選單 / 點地圖）
        │
        ▼
  取得鄉鎮 path 索引 ──► 由 __data__.geometry 算代表座標 (lon,lat)
        │                         │
        ▼                         ▼
  複製官網 path 畫紅框      經緯度→像素座標 (px,py)
        │                         │
        │                         ▼
        │               抓 API 影像清單（16 格）
        │                         │
        │                         ▼
        │           逐張載入 PNG → canvas 取 41×41 鄰域像素
        │                         │
        │                         ▼
        │              顏色判讀 → 雨量等級 + 覆蓋%
        ▼                         ▼
   地圖紅框標示 ◄──────► 面板表格（時間 × 等級 × mm × 覆蓋%）
```

### 5.1 三種選點方式的統一化

- **下拉選單**：縣市→鄉鎮，鄉鎮 option 的 `value` 直接帶 path 索引
- **地圖點選**：（修正後）螢幕座標 → 經緯度 → GeoJSON 命中 → path 索引
- 兩者最終都收斂到「path 索引」，再走同一條查詢流程

### 5.2 紅框繪製（抗縮放關鍵）

- 複製官網自己的 path（`paths[idx].cloneNode`），設 `stroke:red` + `vector-effect:non-scaling-stroke`
- 以 `setInterval`（1.2 秒）+ `resize` 監聽重繪
- **嚴禁使用 MutationObserver**（見 §6.1）
- ⚠️ 此法在雨量模式下會錯位，見 §4.2 末

## 6. 踩雷紀錄（後續迭代務必留意） 〔歷史·只增不改〕

### 6.1 🔴【最嚴重】MutationObserver 無限迴圈凍結分頁

- 症狀：append 紅框 → 觸發 observer → 再 append → 再觸發……**無限迴圈凍結整個 renderer**（JS timeout、截圖失敗、重載無效）
- 修正：**完全放棄 MutationObserver**，改用 `setInterval` + `resize` 監聽重繪。犧牲約 1 秒延遲換取穩定
- 教訓：任何「修改 DOM 又監聽同一 DOM」的機制都要有防遞迴保護，或乾脆不用

### 6.14 【v1.9】並行查詢競態：「A 村的名稱配 B 村的數字」

- 症狀：選村里後狀態列顯示「✅ 屏東縣獅子鄉**竹坑村**（**225** 個雷達格）」——
  225 格是楓林村的，名稱卻是竹坑村。表格內容也可能整張是上一個選擇的資料。
- 成因有兩層：
  1. **兩次 `applySel()` 並行**：選村里會同時觸發「範圍自動切到整個村里」與
     「村里變更」兩條路徑，各發一次 `runQuery`；先發的（舊選擇）後完成，
     於是覆蓋了新結果。查詢時間受快取命中影響，順序不保證。
  2. **狀態列的格數讀全域 `curMk`**：即使 render 的 label 來自那一次查詢，
     格數卻是「當下」的遮罩 → 兩次查詢的資訊被混在同一行。
- 修正：① 每次選取遞增 `queryGen`，`runQuery` 在 render 前比對世代，
  過期就整批丟棄（背景 silent 重查帶當下世代，期間使用者換選取也會被丟棄）；
  ② `raw`（格數）改由該次查詢隨結果傳遞，不再從全域讀。
- 這個缺陷 v1.8 就存在（快速切換半徑時），v1.9 因為多了一層下拉而變成必然觸發。
- 教訓：**非同步查詢一定要有世代／請求 id**。只要 UI 能在前一次完成前再次觸發，
  「後發先至」就會發生；而**顯示用的資料必須跟著那一次的結果走**，
  不能一半來自參數、一半來自全域狀態。

### 6.13 【v1.8】「清掉 → 定時器又畫回來」：關不掉的地圖標示

- 症狀：按面板 ✕ 後 `clearShapes()`（v1.7 以前是 `removeOutline()`）確實清掉了標示，
  但 600ms 後標示又出現在地圖上，關不掉。
- 成因：重繪定時器的條件是 `sig!==lastSig || !document.getElementById('rhoutline')`
  ——「找不到框」本來是用來修復被官網重繪吃掉的框，但**主動清除也符合這個條件**，
  於是下一個 tick 立刻把它畫回來。
- 這是 v1.1 起就存在的缺陷，只是 v1.7 以前只有一條紅色鄉鎮外框，不太顯眼；
  v1.8 多了黃色圓圈與圓心點之後就變成明顯的「畫面殘留」。
- 修正：定時器與 `resize` 監聽都先檢查 `p.style.display==='none'` 才動作
  （與 v1.7 自動更新驅動器的「隱藏即停」同一個判斷）。
- 教訓：**「狀態不存在」和「使用者要求它不存在」是兩件事**。用「元素不見了」當
  自我修復的觸發條件時，必須排除「是我自己把它拿掉的」這種情況。

### 6.2 白色界線被誤判為豪雨 → **v1.1 已作廢**

- 症狀：某鄉鎮每個時段都顯示「豪雨 100%」，實際無雨
- v1.0 根因判斷：雷達 PNG 的地理界線是白色，與豪雨同色 (255,255,255)
- v1.0 修正：白色改為「候選豪雨」，僅當鄰域同時有強降雨色才算豪雨
- 🔴 **v1.1 翻案**：真正的根因是**看錯圖**。工具當時取樣的是 dBZ 回波圖
  （該圖白色 = 最強回波），但需求要的是雨量圖。**雨量圖的白色是最低階 0mm**。
  換用 `_rain.png` 後白色本來就代表無雨，此補丁**已移除**。
- 教訓：先確認**資料來源是否正確**，再去修判讀邏輯。針對錯誤資料源打的補丁，
  即使當下讓症狀消失，也是在錯誤的地基上疊工。

### 6.6 【v1.1】3D 透視變換讓 getBoundingClientRect 失去意義

- 症狀：以底圖 `<img>` 當座標錨點，量到長寬比 4.66（應為 1.294）
- 根因：`#TAIWAN_DBZ_id` 帶 `matrix3d(...)` 立體傾斜變換，
  `getBoundingClientRect()` 給的是投影後梯形的**外接框**，非線性
- 修正：改用未受變換影響的 `.domain_cls` 容器（見 §2.9）
- 教訓：任何用 rect 做線性座標換算的地方，都要先確認該元素及其祖先鏈**無 3D 變換**，
  並用「長寬比是否等於資料源長寬比」當作快速自我檢查

### 6.8 【v1.3】用方形視窗代表不規則區域，會系統性低估

- 症狀：沿海／小面積鄉鎮的覆蓋% 恆為 0，使用者肉眼看到有雨卻查不到
- 根因：以重心取 41×41 方形取樣，分母含海面與鄰鎮。
  **代表區域的形狀不對，統計就沒有意義**
- 修正：改用鄉鎮實際多邊形當遮罩（§7.3）
- 教訓：只要在做「某區域的比例統計」，分母就必須是**該區域本身**，
  不能用外接方形近似。沿海、狹長、破碎（MultiPolygon）的區域誤差最大

### 6.9 【v1.3】對小數值無條件取整會製造假的 0

- 症狀：實際 0.3% 的覆蓋率顯示成 `0`，與「無雨」無法區分
- 修正：分級格式化——`<0.1` 顯示「<0.1」、`<10` 保留一位小數
- 教訓：**「0」和「接近 0」在語意上完全不同**。顯示層的取整會抹掉這個差別，
  讓使用者誤以為系統壞了

### 6.12 【v1.6】只自動化「程式碼」而沒自動化「文件」，說明會默默過期

- 症狀：安裝說明的雨量對照表從 v1.0 起就沒更新過，一路錯到 v1.5
  - 仍寫「豪雨 ≥17mm ＝ 白色」（v1.1 已翻案：白色是 0~0.1mm 無雨）
  - 色塊仍是 **dBZ 舊色盤** `#00ffff` `#0000ff` `#00c800`，不是雨量圖的 17 色
  - 仍寫「首次查詢約 10–20 秒」（v1.2 並行化後約 1 秒）
  - 仍寫「表格前 3 列為過去觀測」（v1.4 已改為「類型」欄）
- 根因：每次發版我都用腳本自動替換 HTML 裡的 bookmarklet blob，
  **但只換 blob，沒動說明文字**。自動化製造了「已經更新過」的錯覺，
  反而讓人不會去檢查其餘內容
- 修正：v1.6 讓對照表、版本、秒數等敘述**全部由 `rain.js` 的常數產生**，
  文件與程式碼共用同一份真相，結構上不可能不同步
- 教訓：**部分自動化比完全手動更危險**。手動時你知道要檢查全部；
  半自動時你會以為工具都處理好了。自動化的邊界必須明確標示出來

### 6.11 【v1.5】用固定亮度門檻決定文字黑白，會有色卡不合格

- 症狀：色帶 3 `(0,154,255)` 配白字，對比只有 2.97（WCAG AA-large 需 ≥3.0）
- 根因：`亮度 > 0.45 ? 黑字 : 白字` 這種固定門檻，在中間亮度區容易選錯邊
- 修正：**兩種前景色都算一次對比度，取高者**。最差值由 2.97 提升到 4.44
- 教訓：自動配色不要用亮度門檻近似，直接算對比度成本極低且不會有邊界誤判

### 6.10 【v1.3】重入保護沒帶版本，導致新版永遠載不進去

- 症狀：使用者換了新書籤，行為卻完全沒變，仍出現舊版的 Bug
- 根因：進入點的重入保護只檢查 `window.__RH_ACTIVE`：
  ```js
  if(window.__RH_ACTIVE){ var ep=...('rhpanel'); if(ep){ep.style.display='block';return;} }
  ```
  只要頁面上**已經跑過任何一版**，點新版書籤就只是把**舊版面板**重新顯示出來，
  然後 `return` — 新版程式碼一行都沒執行
- 修正：改為**版本感知**——同版本才復用面板；偵測到版本不符就把
  `rhpanel` / `rhoutline` / `rhoverlay` 全部移除後重建
- 驗證：模擬「舊版已在跑」（`__RH_ACTIVE=true` 但 `__RH_VER` undefined）
  再跑 v1.3 → 舊面板被移除、`panelCount:1`、`__RH_VER:"1.3"`、摘要列出現 ✅
- 教訓：**單例守衛必須帶版本識別**。否則熱更新型的交付物（bookmarklet、
  user script、注入式外掛）會出現「明明換了新版卻沒生效」這種極難自我察覺的問題。
  面板標題列顯示版本號也是必要的，讓使用者能自行確認跑的是哪一版

### 6.7 【v1.1】時間軸播放時底圖 `<img>` 會被抽換

- 症狀：座標換算間歇性失敗，`getRaster()` 偶爾回 null
- 根因：官網播放動畫時會替換／移除 `<img>` 元素
- 修正：錨點改用生命週期穩定的**容器** `.domain_cls`，而非 `<img>` 本身
- 教訓：選 DOM 錨點時優先挑**容器**，不要挑會被框架動態替換的葉節點

### 6.3 選點偏移約 145 公里

- 修正：改用官網 SVG 的 `getScreenCTM` / `isPointInFill`

### 6.5 頁面重載清空狀態

### 7.8 v1.7 自動更新明細

**問題**：v1.6 以前 `selectTown → runQuery` 只在選取當下跑一次，表格是靜態快照。
官網會隨真實時間推進（每 10 分鐘資料窗口滑動），但工具選完就「停住」：黃底「現在」列、
實況/預報分隔線凍結在選取時刻，官網新產生的影像也永遠補不進來。

**做法**：`selectTown` 記住 `curMk`/`curLabel` 並重置驅動器狀態，一個常駐 `setInterval`
（`DRIVE_TICK` = 30 秒）分兩種更新：

| 情境 | 觸發條件 | 動作 |
| --- | --- | --- |
| 輕量重繪 | `winKey(now) === updWindowKey`（同一個 10 分鐘窗口）| `renderStored()`：用最後結果 + 當下時間重畫，**完全不連網**。移動「現在」列、實況/預報分隔線、摘要倒數 |
| 完整重查 | 跨過 10 分鐘窗口邊界 | 背景 `runQuery(...,silent=true)`：補進官網新影像。舊格子命中 `sampleCache`，只有新格子下載 |

**關鍵設計**：

- **對齊官網 10 分鐘週期 + 遲發重試**：官網發佈常晚於整點，邊界剛到就抓可能撲空。
  故 `winKey` 一變就完整重查，若最新格時間（`lastLatestT`）沒前進就於後續 tick 重試，
  抓到才把 `updWindowKey` 推進到本窗口；連試 `MAXRETRY`(5) 次仍無新影像則放棄本輪、等下個窗口。
  重查前 `listCacheAt=0` 強制讓 `listCache` 失效，否則 60 秒 TTL 內的重試會讀到舊清單。
- **背景不閃爍**：`runQuery` 加 `silent` 參數，背景重查不清空表格、不顯示「查詢…」進度，
  舊表格一直留著直到新結果 `render` 時原子替換。
- **隱藏即停、重開恢復**：driver 先檢查 `p.style.display`，按 ✕ 隱藏時跳過所有連網與運算；
  面板重新顯示（重點書籤）時 `winKey` 已過期 → 下一個 tick 自動補查追上進度。
  因為 gate 在 display 上，不需跨執行實例傳遞狀態。
- **不動的部分**：取樣演算法、色盤、地圖紅框（紅框本來就有自己的 600ms 定時器）皆未更動。

**實機驗證（2026-07-22，官網 appv2、彰化縣大城鄉）**：以撥快頁面 `Date.now` 跨窗口驗證四項皆通過、無 console 錯誤 — (1) 跨 10 分鐘邊界 driver 自動 silent 重查，表格原子替換無閃爍、「現在」列前移、窗口整體前滑補進新格；(2) 按 ✕ 隱藏後跨多個窗口 **0 重查請求**；(3) 重開工具下一個 tick 自動補查追上；(4) 選取查詢、紅框、實況/預報分隔無回歸。

### 7.3 v1.3 修正明細

**使用者回報**：選彰化縣大城鄉，地圖上明明有雨，結果卻都是 0。

**根因（兩個疊加）**：

**① 取樣範圍是方形，不是鄉鎮**
v1.2 以前：以鄉鎮重心取固定 **41×41 方形視窗**取樣，
分母 = 1681（整個方形），其中含**海面與鄰近鄉鎮**。
大城鄉是沿海小鄉鎮，方形視窗有一大半在台灣海峽上 → 覆蓋% 被稀釋。

**② 覆蓋% 無條件四捨五入成整數**
`Math.round(rain/tot*100)`，稀疏降雨算出 0.3% → 顯示 **0**。

**實測對照**（大城鄉，同一張 `nowcast_202607181610_s03_rain.png`）：

| 方法 | 分母 | 降雨像素 | 覆蓋% |
| --- | --- | --- | --- |
| 舊：重心 41×41 方形 | 1681 | 118 | 7.0 |
| **新：鄉鎮多邊形遮罩** | **1990** | **288** | **14.5** |

> 分母變大、分子卻多了 2.4 倍——因為方形視窗根本沒罩到鄉鎮的主要陸地部分。

**修正做法**：

1. `townMask(idx)` 依鄉鎮 GeoJSON 在影像像素座標系建遮罩：
   - 取多邊形 bbox → 建 canvas → `fill('evenodd')` 畫多邊形（evenodd 正確扣除孔洞／飛地）
   - 讀 alpha 通道當遮罩，`inside` = 鄉鎮內像素數
   - 尺寸夾在 **[48, 512]**：太小取樣點不足、太大浪費記憶體
   - 放大時 `imageSmoothingEnabled=false`，避免插值產生色盤以外的混色
   - 每鄉鎮快取一次，16 張影像共用
2. `sampleOne` 改為只統計遮罩內像素，`cover = rain / mask.inside * 100`
3. `fmtCover()`：`<0.1` 顯示「<0.1」、`<10` 顯示一位小數、其餘取整
4. 判讀快取 key 由 `url|px|py` 改為 `url|鄉鎮索引`
5. 移除已無用的 `lonlatToPx()` / `pathLonLat()`（重心法不再需要）

### 7.6 v1.5 修正明細（等級色塊）

**需求**：雨量等級的顏色要比照**動態雨量雲圖**。

**做法**：等級欄由「小色塊 + 白字」改為**整顆色塊標籤**（chip），
底色直接取該色帶在雲圖中的 RGB，文字色自動計算。

**色盤一致性驗證**（掃描當下一張 `_rain.png` 全圖，統計實際出現的顏色）：

| 雲圖實際色 | 像素數 | 在色盤內 |
| --- | --- | --- |
| 152,255,255 | 83,999 | ✅ |
| 0,206,255 | 57,176 | ✅ |
| 0,154,255 | 46,774 | ✅ |
| 255,255,255 | 28,134 | ✅ |
| 0,106,247 | 22,471 | ✅ |
| 46,156,0 | 19,287 | ✅ |
| 43,255,0 | 14,999 | ✅ |
| 254,254,8 | 7,684 | ✅ |
| 255,156,0 / 255,203,0 | 4,316 / 3,779 | ✅ |
| 254,0,5 / 201,2,0 / 157,0,0 | 1,644 / 1,080 / 223 | ✅ |
| 153,255,255 等 4 色 | 8–18 | 邊緣抗鋸齒混色，最近色比對自動歸位 |

#### ⚠️ 文字對比：固定亮度門檻不夠用

| --- | --- | --- | --- |
| 3 | 0,154,255 | 黑 | 2.97 → **6.02** |
| 10 | 254,0,5 | 黑 | **4.44**（全表最差）|
| 4 | 0,106,247 | 白 | 4.77 |
| 15 | 255,0,247 | 黑 | 5.62 |

**最差對比 4.44**，17 色全數通過 WCAG AA-large（≥3.0），多數也達 AA（≥4.5）。

### 7.7 v1.6 修正明細（交付結構）

**問題**：每次改版 `安裝說明.html` 都要整份重產。實測檔案組成——
總長 54,202 bytes，其中兩段 bookmarklet blob 佔 **50,258 bytes（92.7%）**
（一段在拖曳按鈕 `href`，一段在「手動新增書籤」的 `<textarea>`），
真正的說明內容只有 3,944 bytes。

同時查出一個更嚴重的副作用：**說明文字自 v1.0 起就沒同步過**（見 §6.12）。

#### 結構改法

| 檔案 | 角色 |
| --- | --- |
| `rain.src.js` | 可讀原始碼（含註解），開發用 |
| `rain.js` | terser 壓縮後的產出，**安裝頁實際載入的檔案** |
| `落雨小幫手_雨量查詢_安裝說明.html` | 固定內容，**不再隨版本重產** |

工具由 IIFE 改為具名函式：

```js
window.__RH_MAIN = function(__mode){
  var VER='1.6';
  var PAL=[...]; var LV=[...];
  if(__mode==='meta') return { version:VER, palette:PAL, levels:..., notes:{...} };
  /* 以下為正常執行路徑 */
};
```

安裝頁在載入時做兩件事：

```js
// ① 書籤網址：由函式原始碼即時組出
bmLink.href = 'javascript:(' + encodeURIComponent(window.__RH_MAIN.toString()) + ')();';
// ② 對照表：直接由工具自己的色盤產生
var meta = window.__RH_MAIN('meta');
```

**關鍵：`'meta'` 模式回傳的就是工具執行時用的同一組 `PAL` / `LV`，不是另外維護的副本。**
所以對照表、版本號、查詢秒數等敘述在結構上不可能與程式碼不一致。

#### 為何用 `<script src>` 而非 `fetch`

安裝頁是以 `file://` 開啟的，`fetch()` 讀本機檔案會被 CORS 擋；
但 `<script src>` 讀同資料夾的檔案完全正常。
`Function.prototype.toString()` 則可完整還原函式原始碼（含巢狀函式與常數）。

#### 成效

| 項目 | 改版前 | 改版後 |
| --- | --- | --- |
| HTML 大小 | 55,534 bytes | **7,792 bytes** |
| 改版需異動的檔案 | HTML + JS | **只有 `rain.js`** |
| 對照表正確性 | 手動維護，已過期 5 個版本 | **自動產生，不可能過期** |

#### 驗證（jsdom 實跑）

| 檢查 | 結果 |
| --- | --- |
| 版本標籤 | `v1.6` ✅ |
| 書籤 href 長度 | 24,203 字元 ✅ |
| `href` 與 textarea 內容一致 | ✅ |
| 對照表列數 | 11 列（表頭 + 10 個級距）✅ |
| 對照表內容 | 白色＝0~0.1mm 無雨、17 色帶成對合併 ✅ |
| `rain.js` 缺檔時 | 顯示紅色錯誤提示 ✅ |

#### ⚠️ 這個改法**不解決**的事

書籤一旦拖進書籤列，程式碼就固定在那顆書籤裡。
安裝頁每次載入都會組出最新 href，但**使用者仍須重新拖曳一次**才會拿到新版。

若要連重拖都免除，需改為 loader 架構（書籤只放幾百 bytes 的載入器，
程式碼放遠端）。實測官網 CSP 的 `script-src-elem` 白名單包含
`cdn.jsdelivr.net` 與 `unpkg.com`（`cdnjs` 與 `raw.githubusercontent` 被擋），
故技術上可行且不需自架伺服器，但會押在「官網 CSP 不變」與 GitHub/jsDelivr 可用性上。
**尚未採用**，見 §9。

### 11.4 為何要拆成兩支檔案

書籤網址是從「**安裝頁實際載入的那份程式碼**」用 `toString()` 組出來的，
所以載入哪一份會直接決定書籤大小。實測：

| 安裝頁載入 | `toString()` 長度 | 產生的書籤網址 |
| --- | --- | --- |
| `src/rain.js`（含註解）| 25,978 | **58,518** 字元 |
| `dist/rain.js`（壓縮後）| 14,762 | **24,203** 字元 |

差 2.4 倍，主因是中文註解——每個中文字經 `encodeURIComponent` 會膨脹成 9 個字元。
註解對人有價值，塞進書籤網址則純粹是負擔。

| | `src/rain.js` | `dist/rain.js` |
| --- | --- | --- |
| 角色 | 原始碼，人看的 | 建置產物，機器載的 |
| 誰改 | **開發時只改這支** | terser 產生，**手改會被下次 build 覆蓋** |
| 誰載入 | 沒有人 | 根目錄安裝頁 `index.html` 以 `<script src="dist/rain.js">` 載入 |

```
改 src/rain.js
   ↓ npm run build（npx terser）
dist/rain.js
   ↓ 根目錄 index.html（&lt;script src=dist/rain.js&gt;）載入
書籤網址（頁面即時組出）
```

### 11.5 建置識別碼取代版本號（2026-07-22 改制）

> 前身是「版本號單一來源（`package.json` version → `scripts/version.mjs` 同步 VER/README，`npm version` 升版打 tag）」。
> 該 semver 機制已整組廢除，改為下述「無版本號、記錄式」流程。歷史脈絡見 §7 對應日期列。

**核心觀念：不再有版本號要人維護。** `src/rain.js` 的 `var VER='__BUILD_ID__'` 是佔位符，
`npm run build`（`scripts/build.mjs`）在 terser 壓縮後把它蓋成**當天日期**（`YYYY-MM-DD`）。
這個「建置識別碼」只需要「每次 build 會變」即可滿足兩個執行期用途，不需是 semver：

1. 面板標題／安裝頁顯示「更新 <日期>」，讓使用者知道書籤新舊；
2. 防重複注入 `if(window.__RH_VER===VER)`——舊版殘留時偵測並拆除重建。

| 位置 | 值從哪來 | 要手改嗎 |
| --- | --- | --- |
| `src/rain.js` `var VER` | 佔位符 `__BUILD_ID__` | ✅ 保持佔位符，勿填日期 |
| `dist/rain.js` | `scripts/build.mjs` 蓋當天日期 | ❌ build 產生 |
| 面板標題 / 安裝頁 HTML | runtime 讀 `__RH_MAIN('meta').version`（= 日期） | ❌ 免處理 |
| `CHANGELOG.md` | 人手動加一列（日期＋摘要） | ✅ 每次異動加一列 |

**日常流程（無升版）：**

```bash
# 改 src/rain.js 後
npm run build                 # 壓縮 + 蓋當天日期
# 在 CHANGELOG.md 最上方加一列（日期＋一句摘要）
git add -A && git commit …    # pre-commit 會擋「src 改了但 dist 沒重編」
```

**門禁（`.githooks/pre-commit`，可攜）：** 唯一硬擋是「staged 含 `src/rain.js` 但不含 `dist/rain.js`」→
擋下並提示 `npm run build`；另對「改 src 沒動 CHANGELOG」只印提醒不擋。
每台機器一次性 `git config core.hooksPath .githooks` 啟用（hook 內容隨 repo 版控）。

> 刻意的取捨：git 層級檢查擋得住「忘了 build」，擋不住「手改 dist」或「dist 從更舊 src 編」——
> 後者靠「絕不手改 dist」鐵則補足，對單檔 POC 是合理的輕量方案（不必重編比對、也就沒有日期讓比對失準的問題）。

### 12.1 問題陳述

使用者回報（以屏東縣獅子鄉為例）：

> 範圍太大，雖然可能雨勢很大，但表格上的「覆蓋」只有 1%，可能是在別的地方，落差大；
> 如果可以再縮小範圍，那個「覆蓋」可信度又更高。

量化這個問題（雷達影像 3300×2550 對應 117.1595–123.9804°E、21.2646–26.5353°N）：

| 量 | 值 |
| --- | --- |
| 1 像素的經緯度跨距 | 0.002067°（東西向與南北向相同，等經緯度網格） |
| 1 像素的地面尺寸（緯度 22.1°N） | 約 **0.213 km × 0.229 km** |
| 1 像素的地面面積 | 約 **0.049 km²** |
| 獅子鄉面積 300.1 km² → 遮罩像素數 | 約 **6,150 格** |
| 「覆蓋 1%」代表的雨區面積 | 約 **3 km²** |

結論：覆蓋 1% 在獅子鄉這種山區大鄉，確實可能整場雨都落在鄉的另一角。
使用者的判斷正確——**分母太大就是問題本身**，不是顯示精度問題（§6.9 那次修的是顯示，這次要修分母）。

### 12.2 需求與已驗證的事實

使用者原始期望是「能再選市／里／村／鎮」。實地查證後的事實：

1. **官網沒有村里圖層。** 頁面上唯一的行政界 SVG 是 367 條 path 的鄉鎮層
   （§2.2，來源 `module/nowcast/js/TWN_TOWN_nowcast_app.js`），
   `__data__.properties` 只有 `COUNTYNAME` / `TOWNNAME` 兩個欄位，沒有 `VILLNAME`。
   → 村里必須**自備圖資**，官網撈不到。
2. **外部圖資載得進來，但只能用 `<script>`。** 官網 CSP（2026-07-28 實測）：
   - `script-src-elem` 白名單含 `cdn.jsdelivr.net`、`unpkg.com`、`code.jquery.com`
     → 實測從 `cdn.jsdelivr.net/gh/…` 載入 script **成功**（與 §8「loader 架構」那條的既有觀察一致）
   - `connect-src` 只有 `'self'` 與少數第三方 → **`fetch()` 外部網域全被擋**
     （實測 `raw.githubusercontent.com` 與 `*.github.io` 皆 `Failed to fetch`）
   - `img-src` 只有 `'self' data:` → 外部圖片也擋
   → 結論：村里 GeoJSON 得包成 `window.__RH_VILL = {...}` 形式的 **JS 檔**，經 jsDelivr 用 script tag 載入。
3. **村里不見得比半徑圓有用。** 獅子鄉 8 個村，每村平均約 37 km²（約 760 格），
   只把分母縮小 8 倍；而「以我所在點為圓心半徑 1 km」是 3.14 km²（約 64 格），
   縮小近 100 倍，且語意直接對應「我這裡會不會下雨」。

#### 12.4.3 遮罩：共用 `buildMask()`

把 `townMask()` 裡「bbox → canvas 縮放 → 取 alpha 通道 → 算 inside」這段抽成
`buildMask(mnx,mny,mxx,mxy,drawPath)`，鄉鎮與圓共用，各自只提供 `drawPath`：

```js
townMask(idx)          → buildMask(bbox, 畫多邊形 + fill('evenodd'))   // 沿用 v1.3 行為
circleMask(lon,lat,km) → buildMask(bbox, 畫 ellipse + fill())          // 新增
```

`buildMask()` 相對現行 `townMask()` 的兩個改動：

1. **bbox 夾在影像範圍內**（`0..IW` / `0..IH`）。圓可能跨出雷達圖邊界（離島、極端海岸），
   界外像素 alpha=0 會被 `classify()` 判為 `hit:false`（不計入分子），但仍會被算進 `inside`（分母）
   → 覆蓋% 被無聲稀釋。夾住後分母跟著縮，語意才正確。鄉鎮遮罩不受影響（全在影像內）。
2. **回傳值新增 `sxr` / `syr`（canvas↔原生像素縮放比）與 `raw`（等效原生像素數）**：
   `raw = round(inside × (bw×bh) ÷ (cw×ch))`。canvas 放大不會增加真實樣本，
   `raw` 才是「幾個雷達格」，供狀態列顯示。`sxr`/`syr` 供 `townCenter()` 反算經緯度。

尺寸夾在 48–512 的規則不變（見 §11.2）。半徑 0.5 km 的 bbox 只有約 5×5 原生像素，
會被放大到 48×48 canvas；`imageSmoothingEnabled=false` 已關插值，
每個原生像素變成一塊 ~10×10 的均勻色塊，**不會產生色盤以外的混色，也不會偽造精度**，
效果等同「以面積加權計算圓內比例」，比直接數 16 個整數像素更平滑。

#### 12.4.4 圓的幾何（為何是橢圓）

雷達圖是**等經緯度網格**，1 像素在東西向與南北向都是 0.002067°，
但地面上 1° 經度與 1° 緯度的長度不同，所以**地面正圓在像素空間是橢圓**：

```
緯度 1° ≈ 110.574 km（常數）
經度 1° ≈ 111.320 × cos(lat) km
rx(px) = km ÷ (111.320 × cos(lat)) ÷ (ELON-SLON) × IW
ry(px) = km ÷ 110.574              ÷ (ELAT-SLAT) × IH
```

在緯度 22.1°N 實算：`rx ≈ 4.69 px/km`、`ry ≈ 4.38 px/km`
→ 半徑 1 km 的橢圓面積 `π × 4.69 × 4.38 ≈ 64.5` 格，與 §12.1 的「3.14 km² ÷ 0.049」相符（交叉驗證通過）。

各半徑的樣本量（緯度 22–25° 間差異 < 3%）：

| 半徑 | 地面面積 | 雷達格數 | 覆蓋% 的最小刻度 |
| --- | --- | --- | --- |
| 0.5 km | 0.79 km² | 約 16 格 | 約 6% |
| **1 km** | 3.14 km² | 約 64 格 | 約 1.6% |
| 2 km | 12.6 km² | 約 258 格 | 約 0.4% |
| 5 km | 78.5 km² | 約 1,610 格 | 約 0.06% |
| （獅子鄉全鄉） | 300 km² | 約 6,150 格 | 約 0.016% |

> 這張表也是**取捨說明**：半徑越小，覆蓋% 越貼近你所在位置，但刻度越粗。
> 0.5 km 保留給「就是要看我家上方那一塊」的情境，1 km 是建議預設。

#### 12.4.5 圓心來源

#### 12.4.7 判讀快取 key

現行 `sampleCache` key 為 `rainUrl|idx`。改為 `rainUrl|curKey`：

- 同一鄉鎮的不同半徑 → 不同 key → 各自快取，互不污染（這是**必須改**的，
  否則切半徑會拿到上一個範圍的結果，是靜默的錯誤答案）。
- 切換半徑會重跑 16 張的**解碼與掃描**（約 1 秒），但 PNG 走瀏覽器 HTTP 快取，**不重新下載**。
- 影像清單快取（`listCache`，60 秒 TTL）不受影響。

### 12.5 驗收方式

以屏東縣獅子鄉實測，同一時刻比對：

1. 「整個鄉鎮」→ 記下覆蓋% 與雷達格數（預期約 6,150 格）
2. 切「半徑 1 km」（圓心 = 鄉鎮代表點）→ 覆蓋% 應明顯不同於全鄉值，格數約 64
3. 按「點地圖選中心點」點在**有雨的雨帶上** → 覆蓋% 應接近 100%
4. 再點在**同鄉無雨處** → 覆蓋% 應接近 0%
5. 切換「雨量／雷達回波」模式與縮放視窗 → 黃色圓圈仍套在正確位置（§2.5／§5.2 回歸測試）
6. 面板按 ✕ 隱藏再重開 → 表格會自動追上目前時間（v1.7 回歸測試）

第 3、4 點是這次改動的**核心驗收**：同一鄉鎮內不同位置必須給出明顯不同的答案，
否則就沒解決 §12.1 的問題。

### 12.6 風險與取捨

| 風險 | 評估 |
| --- | --- |

### 13.1 已完成的可行性探測（都是實測，不是推測）

| 項目 | 實測結果 |
| --- | --- |
| 圖資來源 | data.gov.tw **dataset 7438「村里界圖(TWD97經緯度)」**，最新檔 `村(里)界(TWD97經緯度)1150624.zip`（民國 115-06-24 = 2026-06-24），22.4 MB |
| 座標系 | `.prj` = `GCS_TWD97[2020]`、mapshaper 判為 `+proj=longlat +ellps=GRS80` → **就是經緯度**，與官網 GeoJSON 同一套，不需轉換 |
| 編碼 | `.CPG` = **UTF-8**，中文屬性直接可讀 |
| 屬性欄位 | `COUNTYNAME` / `TOWNNAME` / `VILLNAME` / `VILLCODE` / `TOWNCODE`（+ 不需要的 VILLENG/NOTE/ID）|
| 筆數 | 7,986 個村里；裁掉雷達範圍外（東沙、南沙）後 **7,984** |
| **名稱對應（最大風險）** | 官網用「**台**南市」、政府用「**臺**南市」。以 `replace(/臺/g,'台')` 正規化後，官網 **367 個鄉鎮全部對應成功**（差異只有政府多一個官網沒有的「金門縣烏坵鄉」）。已在官網頁面實測比對 |
| 工具鏈 | 本機沒有 GDAL／mapshaper，但 `npx mapshaper@0.6.102` 可直接跑（與專案既有的 `npx terser` 同一風格，免安裝）|
| 簡化＋切檔 | `-simplify interval=60 keep-shapes -split TOWNCODE` → **368 檔、總計 5.8 MB、平均 16 KB、最大 51 KB** |
| 實例 | 屏東縣獅子鄉 `10013320.js` = **8 村**（楓林／獅子／竹坑／草埔／丹路／內文／內獅／南世），17.9 KB；最多村里的是新北市板橋區 **126 里**，42.7 KB |

所以圖資要包成 `window.__RH_VILL['<TOWNCODE>'] = {...}` 這種自我註冊的 JS 檔。

### 13.2 資料管線（新增 `scripts/build-vill.mjs`）

```
政府 zip (22.4 MB)
  → npx mapshaper
      -clip bbox=117.1595,21.2646,123.9804,26.5353   # 只留雷達涵蓋範圍
      -filter-fields COUNTYNAME,TOWNNAME,VILLNAME,TOWNCODE
      -simplify interval=60 keep-shapes              # 60 m 容差（雷達 1 格約 230 m，夠用）
      -split TOWNCODE
      -o format=geojson precision=0.0001             # 約 10 m 精度
  → 包成 JS：data/vill/<資料版本>/<TOWNCODE>.js
  → 產生索引：data/vill/<資料版本>/index.js
```

- **資料版本進路徑**（`data/vill/1150624/…`）：jsDelivr 對 `@main` 有數小時快取，
  路徑帶版本號就不必等快取失效，也能同時保留舊版。`dist/rain.js` 內硬編一個
  `VILL_VER='1150624'` 常數（build 時不需改，換圖資才改）。
- `index.js` 內容：`window.__RH_VILL_IDX = { "屏東縣|獅子鄉":"10013320", … }`（368 筆，約 6–8 KB）。
  key 用**正規化後**（臺→台）的官網名稱，直接對得上官網 SVG 的 `COUNTYNAME`/`TOWNNAME`。
- 每個鄉鎮檔：`window.__RH_VILL['10013320'] = [{n:'丹路村', g:<geometry>}, …]`
  （只留必要欄位，屬性名縮成 1 字省體積）。
- **圖資不進書籤**：書籤網址維持約 31.6 KB，圖資是執行時按需載入。

### 13.6 驗收方式

1. 屏東縣獅子鄉 → 村里下拉出現 8 村；選「丹路村」→ 格數數百量級、覆蓋% 與整鄉不同
2. **同鄉兩個村各查一次**：挑當下雨區內、外各一村，覆蓋% 必須明顯不同（本次核心驗收）
3. 新北市板橋區（126 里）→ 下拉正常、載入 42.7 KB 無感
4. 台北市／台南市（官網「台」vs 政府「臺」）→ 能正確載入（正規化生效）
5. 澎湖／金門／連江離島鄉鎮 → 能載入且遮罩有效
6. 把 `VILL_VER` 改成不存在的值模擬載入失敗 → 降級提示正確、鄉鎮／半徑仍可用
7. 回歸：整個鄉鎮、半徑圓、自動更新、✕ 隱藏／重開、模式切換重繪

| 項目 | 內容 |

| **新增外部相依** | 村里功能依賴 jsDelivr 可用性 + 官網 CSP 繼續放行。專案原則要從「無外部圖資」改成「**工具本體無外部圖資；村里功能按需載入自家託管的政府開放圖資**」→ `CLAUDE.md` 與 README 需改 |

### 13.10 本機測試村里載入（不必 push）

**為什麼不能用 `http://localhost`**：官網 CSP（§2.10）的 `script-src-elem` 白名單只有
`blob:`／`'self'`／jsDelivr／unpkg／code.jquery.com…，localhost 不在其中；`connect-src`
也擋外部 `fetch`。所以「本機伺服器 → 官網頁面」這條路被切斷。

**但 CSP 檢查的是請求 URL，不管回應內容從哪來**，於是有三種本機測法：

| 方法 | 測到什麼 | 備註 |
| --- | --- | --- |
| **DevTools Local Overrides**（推薦） | 真實 URL（cdn.jsdelivr.net）＋真實 `<script>` 載入＋真實 `loadScript()`，內容來自本機檔案 | 見下方步驟；repo 內已有 `.overrides/` 映射資料夾（git 忽略） |
| 直接注入 `window.__RH_VILL_IDX` / `window.__RH_VILL[code]` | 全部下游邏輯（遮罩、下拉、查詢、降級） | `loadVillIndex()`／`loadVillTown()` 會先看 `window` 上有沒有，故這是**合法用法**不是 hack；§7.10 的實測就是這樣做的 |
| 另開 `--disable-web-security` 的 Chrome profile | 全部 | 但 CSP 被關掉，就測不到 CSP 相關行為了 |

**Local Overrides 步驟**（一次性設定）：

1. 產生映射資料夾（已在 repo 內，換圖資版本時重跑）：
   ```bash
   D=".overrides/cdn.jsdelivr.net/gh/<user>/<repo>@main/data/vill/<VILL_VER>"
   mkdir -p "$D" && cp -R data/vill/<VILL_VER>/. "$D/"
   ```
2. 官網頁面開 DevTools → **Sources → Overrides → Select folder for overrides** → 選 `.overrides/`
   → 允許存取。
3. 重新執行書籤並選一個鄉鎮。DevTools 會用本機檔案回應那個 jsDelivr URL
   （Network 面板該請求會標上紫色 override 圖示）。
4. 驗證點：村里下拉有資料 ⇒ 真實載入路徑通了；此時**尚未 push 任何東西**。

> ⚠️ 這只解決「開發者測試」。**真實使用者要能用，圖資一定得放在 CSP 白名單上的公開網域**
> （自家 repo 經 jsDelivr、或發 npm 讓 unpkg／jsDelivr 讀、或 GitHub Gist 經 jsDelivr）。
> localhost 永遠不會在白名單裡——這是官網的設定，不是本工具能決定的。

### 13.11 「完全不上傳」的唯一替代：把圖資內嵌進書籤

實測膨脹率（`encodeURIComponent`，座標數字不編碼、括號與引號才編碼）：**約 1.44×**

| 內嵌範圍 | 原始 | 進書籤後 | 可行性 |
| --- | --- | --- | --- |
| 全台 368 鄉鎮 | 3.83 MB | 約 **5.5 MB** | ❌ 書籤網址過長，不實用 |
| 單一縣市（屏東 33 鄉鎮） | 286 KB | 約 **413 KB** | ⚠️ 勉強可行，但要為每個縣市各產生一支書籤 |
| 單一鄉鎮（獅子鄉） | 16.3 KB | 23.5 KB | ✅ 可行，但使用者得為每個鄉鎮換書籤 |

> 若日後真的要走「零遠端」路線，做法是安裝頁加一個「選縣市 → 產生該縣市專用書籤」的產生器。
> 目前**不做**：一支書籤走天下的體驗比省掉一次 push 重要得多。

### 13.8 明確不做

- **不把圖資內嵌進書籤**：5.8 MB 經 `encodeURIComponent` 會膨脹到數十 MB，書籤網址不可能塞
- **不改**等級演算法、色盤、表格欄位、自動更新節奏
- **不做**跨鄉鎮的村里搜尋（例如「輸入村里名直接跳」）——先把三層下拉做好
